# Hackathon OS

Переносимая основа для Codex: помогает превратить ТЗ одного хакатона в цельный и полезный продуктовый прототип. Шаблон не выбирает стек до разбора задания.

## Создать проект для хакатона

1. На GitHub нажми **Use this template** и создай отдельный репозиторий для хакатона. Выбери приватный репозиторий, если ТЗ или разработка не должны быть публичными.
2. Сохрани оригинальное ТЗ без изменений: вставь его полный текст в `brief.md` или укажи там имя исходного файла и путь/ссылку. Исходный PDF, DOCX или другой документ также приложи к задаче Codex.
3. Открой новую копию репозитория в Codex и отправь текст из [`docs/START-PROMPT.md`](docs/START-PROMPT.md) вместе с исходным ТЗ.
4. Codex следует правилам [`AGENTS.md`](AGENTS.md) и [`docs/WORKFLOW.md`](docs/WORKFLOW.md): разбирает пользователей и бизнес-логику, исследует варианты, выбирает стек, планирует P0/P1/P2, предлагает направления дизайна, согласует превью, реализует продукт и готовит демо.

Каждая копия репозитория предназначена **для одного хакатона**. Для следующего события создай новую копию шаблона; не складывай разные проекты во вложенную папку `events/`.

## Подключить Hackathon OS к существующему проекту

Открой существующий репозиторий в Codex и скажи **«Настрой Hackathon OS под проект»**. По умолчанию Codex быстро изучит основные инструкции и продуктовые документы, создаст краткий профиль с источниками фактов и пробелами и добавит необходимые ссылки на него. Для разбора пользовательских сценариев, бизнес-правил, архитектуры и качества отдельно скажи **«Настрой проект подробно»**. Полный аудит возможностей улучшения запускается командой **«Улучшай проект»**; см. [`docs/PROJECT-SETUP.md`](docs/PROJECT-SETUP.md).

## Что входит в основу

- Продуктовый разбор, бизнес-логика, удобство использования и путь до первой ценности.
- Шаблоны ТЗ, журнала решений, исследования, плана реализации, [выбора дизайна](templates/DESIGN-DIRECTION.md), ретроспективы и задания субагенту в `templates/`.
- Пустое запускаемое приложение [`design-preview/`](design-preview/README.md) для согласования дизайна после разбора ТЗ. Его React/Vite — стек инструмента, а стек будущего продукта выбирается отдельно.
- Приоритизация P0/P1/P2, целевой security review и базовые требования доступности.
- Инструкции для демо, синтетических данных, мок-интеграций и работы без секретов в репозитории.
- Правило не добавлять юридические страницы в обычный проект хакатона, если этого не требуют ТЗ или правила конкурса.
- Отдельный запускаемый по запросу цикл комплексного улучшения существующего проекта с экспертными отчётами и новой сессией реализации.
- Ссылки на публичные UI-реестры в `components.json` для поиска компонентов. Они не предопределяют React, Tailwind или shadcn как стек приложения.

## Дополнительные инструменты

Навыки Codex, плагины, MCP-подключения и авторизация настраиваются отдельно в окружении каждого пользователя. См. [`docs/TOOLS.md`](docs/TOOLS.md). Не сохраняй учётные данные в проекте.

После продуктового разбора, исследования, выбора стека и объёма Codex предлагает 2–3 обоснованных визуальных направления. Пользователь выбирает направление или пропускает превью; только после выбора оболочка наполняется представительными P0-элементами и ключевыми состояниями. После принятия превью Codex продолжает реализацию автономно. Полный процесс и правила использования внешних источников описаны в [`docs/DESIGN-CATALOG.md`](docs/DESIGN-CATALOG.md).

Для повторного аудита уже работающего проекта скажи Codex **«Улучшай проект»**. Codex Desktop/CLI и OpenCode используют общие инструкции и профили специалистов; отчёты и handoff сохраняются локально в игнорируемой Git папке `.improve/`. Глубокий режим, границы реализации и команды запуска описаны в [`docs/PROJECT-IMPROVEMENT-LOOP.md`](docs/PROJECT-IMPROVEMENT-LOOP.md).

## Улучшения шаблона

Предложения по развитию основы можно вносить через GitHub Issues или Pull Requests. Не добавляй в исходный публичный репозиторий приватные ТЗ, выходные данные, секреты и конфигурацию конкретной машины.
